# Claim Boundary

This document explicitly defines what security properties `pqkeystore` claims to provide and what it specifically does not claim.

> **[!WARNING]**
> Always consult this document before assuming security properties. Any new security features must be added here as explicit claims.

## Implemented Behavior (Limited Claims)

* **PQKS framing**: The codec recognizes the `PQKS` magic and supported version, decodes the defined fields, rejects trailing bytes, truncation, unsupported versions and absurd declared field lengths with a controlled `FormatException`. This is format parsing, not a claim that a record or backend index is authenticated against an attacker. Evidence: [`sealed_record.dart`](../lib/src/api/sealed_record.dart) and [`record_invariants_test.dart`](../test/record_invariants_test.dart).
* **Passphrase input policy**: `put` and `use` accept only `PassphraseUnlock`. `PlatformUnlock` and `PassphraseThenPlatform` are `PolicyError` and never reach the crypto adapter. `PassphraseThenPlatform` is not treated as passphrase-only. This is API policy, not a claim that a passphrase KDF has any particular strength. Evidence: [`pq_keystore.dart`](../lib/src/api/pq_keystore.dart), [`provider_lifecycle_test.dart`](../test/provider_lifecycle_test.dart).
* **Share custody, not a ceremony**: `putShare` and a direct `put` of `KeyKind.thresholdShare` require structural metadata (`schemeId`, `ceremonyId`, `1 <= t <= n`, 1-based `participantIndex` in `1..n`) and refuse the write before wrap otherwise. `useShare` unwraps one such record and refuses anything else, including a full key, before unwrap. No method reconstructs a key. This does **not** mean the share bytes are a valid `pqthreshold` share or that a ceremony succeeded. Evidence: [`key_metadata.dart`](../lib/src/api/key_metadata.dart), [`share_custody_test.dart`](../test/share_custody_test.dart), [ADR-0005](adr/0005-threshold-share-boundary.md).
* **Callback cleanup (implemented, scoped)**: `use` / `useShare` take ownership of the buffer returned by `PqKeystoreCrypto.unwrap`, copy it into a `SecretBytes`, and wipe the source with `secureZero` immediately after the copy — including when the copy throws. The callback buffer is wiped with `secureZero` on every exit path. `PqForgeKeystoreCrypto.wrap` also wipes the two package-owned plaintext copies it allocates (the `fromList` export copy and pqforge's `PqExportedKey` copy) and does **not** wipe the caller's buffer. Evidence: [`secret_lifetime_test.dart`](../test/secret_lifetime_test.dart), [`provider_lifecycle_test.dart`](../test/provider_lifecycle_test.dart), [`PROVIDER_LIFECYCLE.md`](PROVIDER_LIFECYCLE.md). **Scope limit:** garbage-collector copies, the immutable passphrase `String`, buffers allocated inside `pqforge` that this package cannot reach, and OS page remanence are not wiped and are not claimed.
* **Argon2id cost bounds**: stored `kdfParams` are checked before unwrap. Out of range, a non-`argon2id` KDF, a non-`aes-256-gcm` AEAD, or a salt shorter than 16 bytes is `FormatError` and the adapter is not called. This bounds a hostile record; it is not a claim about KDF strength. Evidence: [`kdf_bounds.dart`](../lib/src/crypto/kdf_bounds.dart), [`kdf_bounds_test.dart`](../test/kdf_bounds_test.dart).
* **Platform channel contract v1 (client side)**: `PlatformKeystoreBackend` validates IDs, record size, and options before calling native code; refuses to operate on a contract-version mismatch; rejects records whose decoded metadata ID differs from the requested ID; and never silently ignores a storage option (unsupported options fail with `UNSUPPORTED_OPTION`). Evidence: `test/platform_backend_test.dart` against the pure-Dart reference in `test/contract/`. See [`PLATFORM_CONTRACT.md`](PLATFORM_CONTRACT.md).
* **Linux native backend (limited)**: On the evidence of the shared contract suite passing locally against gnome-keyring (Pop!_OS 24.04, Flutter 3.47.5), the Linux plugin stores records in the Secret Service default collection and fails with `UNAVAILABLE`, rather than falling back to files, when no Secret Service is reachable. This is behavioral parity evidence only. The Secret Service has **no per-application isolation**: any process in the same user session can read these items, and at-rest protection depends on the provider (e.g. gnome-keyring, KWallet).
* **Fallback file store (limited, opt-in)**: When a caller chooses `FallbackKeystoreBackend` and the OS secure-storage facility reports `UNAVAILABLE`, sealed records are written as `.pqks` files in a dedicated directory with `0700`/`0600` permissions on desktop POSIX. Their only protection is the crypto provider wrapping inside each record; deletion leaves tombstones so records cannot resurface in the secure store after recovery. This is weaker than OS keychain/keystore protection and is never selected automatically.
* **Metadata AAD binding**: `put` computes canonical metadata AAD and supplies it to the crypto adapter. `use` re-validates every record before the crypto adapter is called: the decoded metadata ID must equal the requested ID and the stored AAD must equal the canonical AAD recomputed from the decoded metadata. A mismatch returns `FormatError` and `unwrap` is never invoked, so a record whose metadata was altered while the stored AAD was preserved cannot produce plaintext through the facade. Evidence: [`pq_keystore.dart`](../lib/src/api/pq_keystore.dart) and [`record_invariants_test.dart`](../test/record_invariants_test.dart), which mutates each authenticated metadata field while preserving the stored AAD and asserts, through a counting crypto adapter, that unwrap is never reached. See [ADR-0006](adr/0006-pqks-record-invariants.md). This claim covers the facade and the codec only; it does not claim that a compromised backend or an attacker who can rewrite a record together with its AAD is detected.
* **Metadata confidentiality**: PQKS serializes `KeyMetadata` in cleartext. Do not place secrets or sensitive personal data in metadata unless the selected backend's confidentiality behavior has been explicitly reviewed.

## Planned Invariant, Not Yet Claimed

* **Complete memory erasure**: the buffers this package owns and can reach are wiped (see *Callback cleanup* above and [`PROVIDER_LIFECYCLE.md`](PROVIDER_LIFECYCLE.md)). Three gaps are recorded against the pinned `pqforge` 0.4.7–0.4.13 and `zeroize` 0.2.0 sources and none is claimable: (1) the Dart GC may copy a `Uint8List` before it is zeroed; (2) the passphrase becomes an immutable `String` (`String.fromCharCodes`, then pqforge's `utf8.encode`) and a `String` cannot be overwritten; (3) temporaries inside `pqforge` that the adapter never receives, and OS page remanence, are out of reach of pure Dart.
* **Isolate offloading of the KDF** (planned, 0.2.0): moving Argon2id off the caller's isolate is a **frame-stability** measure and nothing more. `pqforge` is pure Dart, so the worker allocates its own 64 MiB Argon2id block — isolates give the UI isolate its time back, they do **not** reduce peak memory. No claim of memory reduction, of lower device requirements, or of KDF affordability on a constrained device. See [`AGENTS.md` rule 12](../AGENTS.md) and [`IMPLEMENTATION/CROSS-CUTTING.md`](IMPLEMENTATION/CROSS-CUTTING.md) § C.2.2.
* **Device authentication** (planned, 0.2.0): user presence and biometric options raise the bar for casual access to a record. They are **not** a boundary against a compromised operating system, a rooted device, or an attacker with code execution at or above the keystore. `requireBiometric` on Apple means `biometryCurrentSet`; on Android `setInvalidatedByBiometricEnrollment`, which destroys the key on enrollment change rather than re-prompting. Neither has been exercised on hardware in this repository — see the not-run table required by [`IMPLEMENTATION/020-platform-unlock.md`](IMPLEMENTATION/020-platform-unlock.md) § 4.3.
* **Rotation durability** (planned, 0.3.0): `rotate` writes the successor record before touching the predecessor, so a failure leaves the old record intact and readable. This is a **failure-atomicity ordering argument, not a crash-atomicity guarantee**. No claim is made that a power loss mid-rotation leaves the lineage consistent; journaled or write-ahead rotation is out of scope. See [`IMPLEMENTATION/030-key-lifecycle.md`](IMPLEMENTATION/030-key-lifecycle.md) § 2.3.
* **Backup integrity** (planned, 0.4.0): the `PQBA` manifest's per-record SHA-256 values detect **corruption, truncation and partial writes**. They are not tamper-evident: an attacker who can rewrite the archive can rewrite the manifest. No claim of authenticated backup, of provenance, or of protection against a hostile store. See [`IMPLEMENTATION/040-backup-restore-migration.md`](IMPLEMENTATION/040-backup-restore-migration.md) § 2.2.
* **Metadata confidentiality, restated for v2** (planned, 0.3.0): metadata schema v2 adds `provenance` and `wrapPolicy` to the cleartext `KeyMetadata`. This is a documented property of the format, not a regression, and it widens what an attacker who can read a store can learn. Do not place secrets in metadata. See [`IMPLEMENTATION/030-key-lifecycle.md`](IMPLEMENTATION/030-key-lifecycle.md) § 2.2.

## Non-Claims (What we DO NOT guarantee)

* **Cryptographic Strength**: `pqkeystore` DOES NOT claim that the underlying encryption is strong. The strength is entirely dependent on the injected `PqKeystoreCrypto` implementation.
* **Platform availability or isolation**: Contract v1 has passing on-device CI evidence for Android (API 26, 28, 35), Windows, Linux and iOS (SwiftPM) — CI run 37770086113. The macOS and iOS CocoaPods jobs build but stop at a clear, explicit "no Apple development signing identity" error until a signing identity is provisioned in CI; they are therefore **not** claimed as verified. Even where the suite passes, no claim is made of hardware backing (TEE/StrongBox/Secure Enclave), of equivalent protection across platforms, or of isolation from other processes running as the same user. Windows DPAPI user scope and the Linux Secret Service do not isolate applications from each other.
* **Option enforcement beyond the reported capability set**: A capability is enforced only when it appears in `platformInfo.supportedOptions` on that device at write time. On Android, `afterFirstUnlock` relies on credential-encrypted storage, and `whenUnlocked` on `setUnlockedDeviceRequired`; neither is re-checked if the user later removes the lock screen. Behavior of biometric-bound Apple items after biometric re-enrollment is unverified.
* **Physical erasure**: `delete` is logical deletion. No claim is made that bytes are erased from flash, NTFS, or keychain/secret-service databases.
* **Backup and migration**: Platform records are device-bound. Android and Windows protecting keys do not leave the device/user profile, and Android records are excluded from backup. No restore or cross-device migration is offered.
* **File index authenticity**: There is no index. The file store persists one record per file named `hex(SHA-256(ID)).pqks` (file store v1, ADR-0010), and existence is derived from directory entries cross-checked against the ID embedded in the record, so no persisted data can point outside the backend directory. No claim is made that this protects against an attacker who can write to the store directory: such an attacker can replace a record and its AAD together.
* **Side-channel resistance**: No resistance to timing, power, or memory-snooping attacks is claimed.
* **Callback confinement**: The callback can copy or retain the plaintext it receives. The API cannot prevent caller leakage or copies outside the buffer it clears.
* **Complete memory erasure**: Dart/runtime copies, pqforge-internal temporaries, the immutable passphrase `String`, and OS page remanence are outside what the tests demonstrate. See [`PROVIDER_LIFECYCLE.md`](PROVIDER_LIFECYCLE.md).
* **Threshold validity**: Structural metadata checks do not validate share mathematics, a DKG, or a signing ceremony. `useShare` returns one stored share, never a reconstructed key.
* **Format interoperability**: PQKS is not the pqforge `.pqf` or `.pqfs` content-envelope format. No cross-format import/export compatibility is claimed.

## Current State

> **[!CAUTION]**
> A `PqForgeKeystoreCrypto` adapter exists. Its buffer ownership and Argon2id cost checks are recorded in [`PROVIDER_LIFECYCLE.md`](PROVIDER_LIFECYCLE.md); that record is not an independent security review, and the package is not production-ready. The XOR stub is not part of the published library: it lives under `test/support/` and cannot be imported from `package:pqkeystore`. Removing it from `lib/` is a footgun removal, not a security improvement to any cryptographic path. See [`TRACKER.md`](TRACKER.md) for the remaining release gates.
